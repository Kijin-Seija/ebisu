# Karpathy Skill 参考示例

这份参考用于在启用 `karpathy` skill 后，帮助判断哪些行为符合“四条原则”。

## 1. 先暴露假设，不要静默脑补

用户说：`给用户数据加一个导出功能`

不好的做法：

- 默认导出所有用户
- 默认导出到本地文件
- 默认字段包含全部敏感信息
- 默认格式就是 CSV 或 JSON

更好的做法：

- 先问清范围：全部用户还是筛选结果
- 先问清交付形态：浏览器下载、后台任务、还是 API
- 先问清字段边界：哪些字段允许导出
- 先问清数据量：这会影响同步还是异步方案

## 2. 不要把“简单需求”做成框架

用户说：`加一个计算折扣的函数`

不好的做法：

- 立刻引入策略模式、抽象基类、配置对象
- 预留多种未来折扣类型
- 为暂时不存在的业务分支写大量接口

更好的做法：

- 先实现一个最小函数
- 只有在明确出现第二种折扣规则时，再考虑抽象

## 3. 不要顺手修改无关区域

用户说：`修复登录按钮点击无效`

不好的做法：

- 顺手统一附近文件格式
- 顺手重命名一批局部变量
- 顺手删除看起来没用的旧注释

更好的做法：

- 只修改导致点击失败的逻辑链路
- 如果注意到旁边还有旧问题，在结果里单独提示，但不顺手改

## 4. 把任务写成可验证目标

用户说：`把搜索做快一点`

不好的做法：

- 不澄清“更快”指的是响应时间、吞吐量还是体感速度
- 直接上缓存、异步、索引、分页、骨架屏，全部一起改

更好的做法：

- 先澄清优化目标
- 把任务改写成可验证目标，例如：
  - 常见查询 P95 从 500ms 降到 150ms 以内
  - 搜索结果首屏渲染时间减少 40%
  - 某个慢查询的 explain 计划不再走全表扫描

## 使用提醒

- 这份 skill 不是要求“总是多问问题”，而是要求在关键假设会改变实现方向时，把假设说出来
- 这份 skill 也不是要求“永远只写最小代码”，而是要求不要为不存在的需求提前建复杂结构
- 如果用户明确要求更大范围重构、统一清理或铺基础设施，以用户目标为准
