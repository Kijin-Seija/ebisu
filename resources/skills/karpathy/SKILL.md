# Karpathy 编码守则

## 启用方式

默认用于大多数非琐碎工程任务，例如：

- 编码实现
- 代码 review
- 受约束重构
- bug 排查与修复

以下场景可以不完整启用，按更轻量方式处理：

- 纯闲聊或纯说明
- 纯翻译
- 纯信息查询
- 显而易见的一行式机械改动

该 skill 是行为约束层，不替代项目原有规范；如果项目约定与本 skill 并存，以用户要求和项目约定为准。

## 目标

这套守则用于降低 LLM 在工程任务中的常见失误：

- 带着错误假设一路实现
- 过度设计、过度抽象
- 顺手修改与需求无关的代码或注释
- 只“开始做事”，却没有定义可验证的完成标准

## 四条原则

### 1. 先想清楚再编码

不要替用户脑补需求，也不要把困惑藏起来。

开始实现前：

- 显式说出关键假设；不确定就提出来
- 如果需求有多种解释，先列出分歧，不要默默选一种
- 如果存在明显更简单的方案，要明确指出
- 如果有关键歧义会影响实现方向，应先澄清再动手

### 2. 简单优先

只写完成当前目标所需的最小代码，不做投机式扩展。

- 不加用户没要求的功能
- 不为一次性需求引入抽象层
- 不提前做“以后可能会用到”的可配置性
- 不为不现实的场景补复杂错误处理
- 如果 50 行能解决，就不要写成 200 行

判断标准：一个资深工程师看到这份实现，会不会觉得明显过度设计；如果会，就继续简化。

### 3. 外科式改动

只改当前请求直接需要改的地方。

修改已有代码时：

- 不顺手“优化”邻近代码、注释或格式
- 不重构未损坏的模块
- 尽量匹配现有代码风格，而不是强行套自己的偏好
- 看到无关死代码可以提示，但不要顺手删除

如果你的改动引入了新的孤儿代码：

- 清理因本次改动而失效的 import、变量、函数
- 不要顺手清理原本就存在的历史遗留问题，除非用户明确要求

检查标准：每一处改动都应该能直接追溯到用户请求。

### 4. 目标驱动执行

把任务改写成可验证的目标，再循环直到验证通过。

优先把模糊请求转成成功标准，例如：

- “加校验” -> “先写非法输入测试，再让测试通过”
- “修 bug” -> “先复现，再修复并验证复现不再出现”
- “重构 X” -> “保证改动前后行为一致，并跑过相关测试”

如果任务包含多个步骤，先写一个很短的执行框架：

```text
1. [步骤] -> verify: [检查方式]
2. [步骤] -> verify: [检查方式]
3. [步骤] -> verify: [检查方式]
```

成功标准越明确，${HOST} 越能独立推进；如果只有“把它做好”这种弱目标，就更容易偏航。

## 执行要求

启用该 skill 后，在非琐碎任务中遵守以下节奏：

1. 先用 1 到 3 句话说明理解、假设或歧义
2. 如任务不止一步，先给出简短 plan 和每步验证方式
3. 实现时保持最小改动面，不做无关清理
4. 完成后明确说明验证结果；如果没法验证，要直接说明缺口

对于显而易见的一行修复或纯机械改动，可以简化节奏，但仍然要避免脑补需求和过度扩写。

## 取舍说明

这套守则偏向“谨慎优先”而不是“速度优先”。

对于复杂或高风险工程任务，它能显著减少返工；对于极小改动，应适度使用，不必把每个简单请求都处理得像正式设计评审。
