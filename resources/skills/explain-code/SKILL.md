## Ebisu 运行方式

先读取入口返回的经验与变量。运行工具必须通过 `${EBISU_CLIENT} --terminal ${HOST_KEY} run --skill explain-code --path "$PWD" --script scripts/脚本名 -- 参数`，不从安装目录推导项目、不直接改写中央文件。

# 说明书式代码解释

## 调用边界

仅在用户显式写出 `${INVOKE}`，或明确要求“使用 explain-code skill”时启用。不要因为用户普通地询问代码而自动套用。

该 skill 只规定如何分析和解释代码，不扩大任务权限。除非用户同时明确要求修改，否则保持只读。

## 目标

让读者在答案的第一部分就能回答：

- 这段程序解决什么问题
- 什么事件触发它，最终产生什么结果
- 哪几个组件承担关键职责
- 应该去哪些文件或符号继续阅读

答案应按用户的问题组织，而不是按 agent 的搜索顺序、目录顺序或源码出现顺序组织。

## 先建立地图

开始解释前，先确认用户关心的入口、范围和预期深度。如果问题很宽，选择最能代表真实行为的一条主路径，并明确说明本次解释覆盖的范围；除非不同选择会显著改变答案，否则不要为了范围问题停下来追问。

优先给出以下内容：

1. **一句话结论**：用普通语言说明整体行为。
2. **主流程**：用“触发 -> 处理 -> 结果”或短编号步骤描述正常路径。
3. **角色地图**：涉及三个或更多关键组件时，用表格说明“组件 / 职责 / 与谁协作”。
4. **源码落点**：列出支撑结论的少量关键文件、函数或类型。

这些不是强制标题。答案很短时可以合并，但不能省略读者理解主线所需的信息。

## 分层展开

在主线清楚之后，再按需要逐层解释：

1. 用户或业务层看到的行为
2. 模块之间如何协作
3. 关键实现机制与数据变化
4. 设计原因、限制和取舍
5. 错误路径、边缘情况和例外

同一段尽量只讨论一个抽象层次。不要在一句话里同时混合业务概念、框架机制、线程调度和异常分支。

如果用户只问一个局部问题，直接回答该问题，再补足理解它所需的最小上下文；不要借机介绍整个系统。

## 术语与代码标识符

- 术语第一次出现时，先说它在当前程序中的具体作用，再给出正式名称。
- 缩写第一次出现时展开全称，除非它是用户已经在使用的项目常用词。
- 优先使用具体动词，例如“读取配置”“校验请求”“写入数据库”，少用“处理”“协调”“抽象”等空泛表达。
- 代码标识符用于定位证据，不用来代替解释。先说明 `PaymentService` 做什么，再讨论它的方法名。
- 连续出现多个术语时，改写成具体的因果或时序关系。

例如，不要只写：

> Controller 通过依赖注入调用 Service，再由 Repository 完成持久化。

优先写成：

> 用户提交数据后，请求入口先检查参数，业务模块决定是否允许保存，数据访问模块最后把结果写入数据库。代码里这三个角色分别叫 `Controller`、`Service` 和 `Repository`。

## 证据与不确定性

- 将关键结论映射到真实文件、符号或行号；不要罗列所有浏览过的文件。
- 明确区分源码直接表明的行为与基于命名、配置或调用关系作出的推断。
- 如果运行时行为依赖配置、动态分派、生成代码或外部服务，说明证据边界。
- 遵守项目 `${INSTRUCTIONS_FILE}` 中的代码探索规则；存在 CodeGraph 索引时优先使用它。

## 深度模式

用户可以在调用时指定深度：

- `${INVOKE} quick`：只给结论、主流程和关键源码落点。
- `${INVOKE}`：默认模式；补充角色分工、关键机制和必要术语。
- `${INVOKE} deep`：在概览之后展开完整调用路径、状态变化、异步边界、错误路径和设计取舍。

即使是 deep 模式，也必须先给概览，再给细节。

## 避免

- 按“我先搜索了什么、后来发现什么”的调查时间线写答案
- 按文件逐个复述代码，却不说明文件之间的关系
- 在主流程清楚前堆叠框架术语、设计模式和边缘情况
- 把所有分支写成同等重要，导致正常路径不突出
- 逐行翻译源码，或用很长的调用链代替行为解释
- 为显得严谨而加入与用户问题无关的背景知识
