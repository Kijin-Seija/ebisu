## Ebisu 运行方式

先读取入口返回的经验与变量。运行工具必须通过 `${EBISU_CLIENT} --terminal ${HOST_KEY} run --skill debug-manual --path "$PWD" --script scripts/脚本名 -- 参数`，不从安装目录推导项目、不直接改写中央文件。

# Debug Manual

## 触发条件

只在用户明确要求时启用，例如：

- `使用 debug manual`
- `${INVOKE}`
- `请走 debug-manual`
- `你先加日志，我自己操作后把结果发你`

如果用户没有显式要求，不要默认启用。

## 目标

该 skill 用于在无法或不适合使用自动化浏览器、也不适合启动本地日志服务器时，通过代码临时打点建立证据链：

1. 在最可能的代码路径加上临时 `console` 日志
2. 让用户按指定步骤自行复现
3. 让用户回传日志内容
4. 基于日志分析问题，必要时进行第二轮更精准打点
5. 修复后移除临时日志

## 核心原则

### 不启动本地日志服务器

进入 `debug-manual` 后：

- 不要启动 `debug-steps` 的本地日志服务器
- 不要要求页面接入额外的 `/log` HTTP 上报
- 不要把这个模式临时改造成另一种远程日志采集方案

### 打点要可识别、可回收

临时日志应满足：

- 前缀明确，例如 `[debug-manual][checkout]`
- 字段尽量结构化，便于用户复制和 agent 分析
- 范围尽量收敛，只覆盖当前怀疑路径
- 问题解决后默认移除，不要把临时噪音永久留在代码里

### 先看日志，再做结论

即使这些日志是 agent 自己加进去的，也必须先读取用户回传的真实输出，再做判断。

如果当前日志还不足以证明判断成立，应继续补打点，不要跳过证据闭环直接修代码。

## 标准流程

### 1. 先确定打点位置

先阅读相关代码，选出最能回答当前问题的几个节点，例如：

- 事件入口是否触发
- 关键参数进入组件或函数时的值
- 请求发出前后的 payload / response
- 状态更新前后的差异
- 异常捕获分支是否被执行

不要一上来就在大量文件里铺满日志。

### 2. 添加临时日志并说明复现方法

修改代码时，应让日志具备稳定格式，方便用户直接复制。

然后明确告诉用户：

- 需要执行哪些操作
- 去哪里看日志
- 需要回传哪些片段

例如浏览器 console、开发服务器终端输出、Electron 控制台等。

### 3. 基于用户回传日志建立证据

收到日志后，先区分：

- `日志证据`：真正打印出来的内容、顺序、状态值、报错
- `分析推断`：这些内容映射到的代码路径和根因

如果日志不足以证明判断成立，就继续做第二轮更精准的打点。

### 4. 修复并移除临时日志

当证据已经足够支撑判断后，再进行正式修复。

修复完成后，默认要把本轮临时 `console` 打点移除；除非用户明确要求保留长期诊断日志。

## 行为约束

1. 不要用 Playwright 或真实浏览器（CDP）自动操作页面。
2. 不要启动本地日志服务器。
3. 不要让用户在没有明确指引的情况下自己猜该提供哪些日志。
4. 不要把临时调试日志残留到最终提交里，除非用户明确要求保留。

## 推荐输出骨架

在 `debug-manual` 中，尽量按这个顺序对用户汇报：

1. `我准备在哪些位置加临时日志`
2. `这些日志分别想验证什么`
3. `请你按哪些步骤复现，并把哪些输出发我`
4. `我从回传日志里确认到的现象`
5. `接下来是继续补日志，还是已经足够进入修复`
